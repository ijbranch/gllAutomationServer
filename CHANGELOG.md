### Added
- (2026-10-30) **Protocol 0.13: `click_at`, `drop_files`, a fuller `dialogs`, and `TAutomationServer.RenderControl`** - `gllAutomationServer.pas`, `Tests\TestGllAutomationServer.pas`, `Help.md`, `Users Guide.md`.  `click_at` (`form?`, `name`, `x`, `y`, `shift?`) posts a real left click at a point of a control, in its client coordinates, to whatever window lies there, as Windows would route it; Shift and Ctrl travel in the messages' key flags.  `drop_files` (`form?`, `name`, `files`, `x?`, `y?`) drops files as Explorer does, through `WM_DROPFILES` to the nearest window up the chain that accepts files.  Both refuse what a user could not do: a point outside the control (`OutsideControl`), a hidden or disabled window or one under a modal (`NotClickable`), no window that accepts files (`NoDropTarget`), a file that does not exist (`NoFile`).  `dialogs` adds, without removing anything: per window `modal` and `texts`, per button `hwnd` and `clickable`, `mainThreadBusy` on the list, a `modalOnly` filter, an `hwnd` that narrows a click to one window, and on a click `hwnd`, `buttonHwnd`, `outcome` (`gone` / `covered` / `unchanged`) and `method`.  `RenderControl` renders any control a registered worker-thread command resolves, exactly as `screenshot` renders a named one (the shared `RenderPlanned`), for targets the built-in addressing cannot name: gllIdeAutomation's designer screenshot.  **Why:** GxInspect's `CLICKAT`, `DROPFILES` and `DIALOGS` / `DISMISS` covered what ours could not (Ian, 2026-10-30).  Ported or derived from GxInspect (svn r6031, `host\GxInspect_Server.pas`): the click-ability rule (`GxCanBeClicked`), the modal-window rule (`EnumDialogProc`), the three click outcomes (`CmdDismiss`), the window-at-point descent (`TryGetWindowAtPoint`) and the `CF_HDROP` block (`GxMakeHDrop`); the unit header credits them.  Not done: an OLE drop target (`RegisterDragDrop`) is not reached, where GxInspect tries it first.  11 new tests (33 in the server fixture): red first on the old build, each on its own assertion (the double click showed `Expected [1] but got [2]`), then green; mutation-proved by hand, since the suite links the package's DCUs and `test_mutate` cannot rebuild them: 6 mutants (chain check, ambiguity, a second `BM_CLICK`, `hwnd` ignored, Shift dropped, drop point zeroed), each killed by its own test.
- (2026-10-13) **Protocol 0.12: `screenshot` renders a named control or form, and takes `maxWidth`** - `gllAutomationServer.pas`, `Tests\TestGllAutomationServer.pas`, `Help.md`, `Users Guide.md`, `CLAUDE.md`, `gllIdeAutomation\Help.md`, `gllIdeAutomation\Users Guide.md`. With a `name`, or a `form` and no `area`, the target's top-level window is rendered through DWM (`PrintWindow` with `PW_RENDERFULLCONTENT`) and the target cropped out, at the host's logical size; the reply adds `target` and `renderer`. **Why:** the capture modes copy screen pixels, so a covered or off-screen window came out as whatever was in front of it, silently; and a 3840-wide monitor capture is shrunk on reading until small text is unreadable, where a control crop keeps full detail. `maxWidth` scales any screenshot down (`HALFTONE`), with `sourceWidth`/`sourceHeight` in the reply. Four silent failures found and designed out on the way, each measured: DWM `PrintWindow` from the window's own thread returns FALSE (planning now runs on the main thread, rendering on the worker); the classic `PrintWindow` on a VCL child control returns TRUE with a blank image; a 24-bit target bitmap does the same (now 32-bit); and a VCL bitmap canvas used off the main thread loses its DC unless locked. The VCL's `PaintTo` remains as a fallback (`renderer:"paintTo"`) but draws only the first child of a form. New codes `NotVisual`, `NotShowing`. 4 new tests (22 in all): an off-screen memo renders in its own fuchsia, a `TLabel` crops in its own yellow, a whole form includes its children, `maxWidth` scales; they ignore themselves in Session 0 (no desktop), so `test_run` reports 18 passed / 4 ignored and a desktop run 22/22. Mutation-proved: a 24-bit bitmap turns the three pixel tests red.

### Fixed
- (2026-10-30) **Inside the IDE no `ide_*` / `debug_*` command was registered: the server answered ping and nothing else** — `gllAutomationServer.pas`.  Found by the first live run of 0.13.  gllIdeAutomation's first `RegisterCommand` met a nil command table, an access violation in `TMonitor.GetMonitor( nil )` that its start-up swallowed.  **Why** the table was nil is not established: the IDE package requires this one, whose initialization should have run first (an independent review made that point).  The table is now created on first use by `CommandTable`, under an atomic compare-exchange, which removes the failure whatever the order; the unit's initialization no longer REPLACES a table registrations already went into; and a registration after this unit's finalization is refused (`EInvalidOpException`) rather than re-creating a table nothing frees.  Proved live: the start-up log reads "IDE commands registered" and every command answered.  The start-up log records any recurrence.
- (2026-10-30) **`dialogs`, second pass after an independent review: two same-caption buttons in one window could never be clicked, a slow handler read as `unchanged`, and a message box's OK was refused as ambiguous** - `gllAutomationServer.pas`, `Tests\TestGllAutomationServer.pas`, `Help.md`.  Each red first, each mutation-proved by hand.  (1) `AmbiguousButton` said to pass `hwnd`, which names only the window, so two `Browse...` buttons in one dialog were refused every time where the old code clicked the first; `buttonHwnd` (the handle the listing reports, now also in `error.data`) clicks exactly that button.  (2) The outcome was judged from when the click was POSTED, so an OK whose handler ran for 2.5 s, or a busy main thread, answered `unchanged` and `dismissed:false` while the click was still queued or running, and a caller that retried clicked twice.  A hidden window of the main thread (`TClickMarkWindow`) now takes a marker posted behind the click - posted messages are handled in order, and a SENT probe would have overtaken it - and the outcome is judged once it arrives; after `wait` ms (default 5000) the answer is `pending`, never `unchanged`.  The 1.5 s look is now timed by a stopwatch: counting 25 ms sleeps had stretched it to about 1.9 s, which is why the first test of this passed on the old code.  (3) A Win32 message box disables only its owner, so an `OK` on another open window was clickable too and the new ambiguity rule refused what the old code had served; when several windows match, the one in a modal window is now clicked, and only several modal matches are refused.  Also: `mainThreadBusy` is asked BEFORE the listing (afterwards it measured only whether the thread had caught up) and of the marker window, since a console host has no `Application.Handle` and always read "not busy"; `texts` reads static controls by the system class they are built on, so a VCL `TStaticText` is found, under a 0.5 s budget per window with `textsComplete` saying when it ran out or a text was cut at 4096 characters.  Declined: a sharper modal test, documented on `WndIsModal` and in `Help.md` instead (a modeless window owned by the window a message box disabled reads as modal; the harm is bounded because two modal matches are still refused).
- (2026-10-30) **`RegisterCommand` let a second provider take a name over, and the first one's `UnregisterCommand` then removed the second's command** - `gllAutomationServer.pas`, `Tests\TestGllAutomationServer.pas`, `Help.md`.  `AddOrSetValue` replaced the handler silently.  A name already registered is now refused with `EArgumentException` (unregister first to replace one); nothing in the estate re-registered a name (checked: gllIdeAutomation, the DBiWorkflow tree, GITLAKLib, GITLAKMCP).  Red first; mutation-proved.  The trap is GxInspect's "Two plugins, one command name".
- (2026-10-30) **`dialogs` clicked a button TWICE, clicked one a user could not reach, and clicked the first of several of the same caption** - `gllAutomationServer.pas`, `Tests\TestGllAutomationServer.pas`.  Three faults in the click path, each now covered by a test that was red on the old build.  (1) After a sent `BM_CLICK` the mouse-message fallback fired whenever the button's window still existed, which it always does straight after a click (a modal form is torn down only when its loop unwinds), so a button that does not close its window ran twice (measured: 2 clicks for 1), and a nested modal first held the send for its 5 s timeout.  The click is now POSTED once: `BM_CLICK` to a button built on the system `Button` class (`RealGetWindowClass`), the mouse messages only to one that is not (Ethea's `TStyledButton`), never both.  (2) Only the button's own visible/enabled state was checked, so a button in a window with a modal on top was clicked although a user could not reach it; every window up the chain must now be enabled (`NotClickable`, with the buttons in `error.data`).  (3) The first match across every top-level window was clicked; two clickable matches are now refused (`AmbiguousButton`, listing each with its window), and `hwnd` says which window is meant.  `dismissed` keeps its meaning, the window the click was in went away, now judged over 1.5 s (was 0.75 s) and on the dialog rather than the button.  Found from GxInspect's README, "When the IDE is asking something" (Ian, 2026-10-30).

## [1.0.0] - 2026-10-13

### Added
- (2026-10-13) **The package: the server leaves GITLAKLib and becomes one shared copy** - `gllAutomationServer.pas`, `gllAutomationServer.dpk`, `gllAutomationServer.dproj`, `Tests\gllAutomationServerTests.dpr`, `Tests\gllAutomationServerTests.dproj`, `Tests\TestGllAutomationServer.pas`, `README.md`, `Help.md`, `Users Guide.md`, `LICENSE`. The unit lived in GITLAKLib, with a renamed, hand-synced copy in gllIdeAutomation (`gllIdeAutomation.Server`) because a unit may exist in only one loaded package. The copies drifted 283 lines apart once, and every change had to be made twice. Now there is one: the DBiWorkflow applications link it through the library path (`37.0\<Platform>\Release`), and gllIdeAutomation `requires` this package. Runtime-only, Win32 + Win64, four modes clean, version 1.0.0.0 with build auto-increment on. MIT, as the copy in gllIdeAutomation already was. **Why a package of its own:** it was also GITLAKLib's only reason to require Indy.
- (2026-10-13) **`TAutomationServer.Start` takes `ADisableIdleTimers`** (default True) - `gllAutomationServer.pas`. The one behavioural difference between the two copies - an application's idle timers are disabled before each command so it cannot log itself out mid-test; the IDE's belong to its plug-ins - is now chosen by the host. gllIdeAutomation passes False.
- (2026-10-13) **`TAutomationServer.ResolveForm` / `ResolveComponent` are public** - `gllAutomationServer.pas`. A registered command addresses forms and components exactly as the built-ins do: paths, synthetic names, `Ambiguous`. gllIdeAutomation's `tree_text` moved out of the server onto them.
- (2026-10-13) **Protocol 0.11 - components: reachable, path and synthetic names** - `gllAutomationServer.pas`. A `name` the form does not own is found anywhere reachable from it: a frame's controls, or a control docked in without being owned (an add-in's frame in the IDE, which `FindComponent` could never see). A dotted path narrows it (`fraAddress.edtTown`). An unnamed component has a synthetic name (`@TButton#2`, numbered per class, the form's own components first), which `tree` reports and every command accepts. A name several components share fails `Ambiguous`, with a path for each in `error.data.candidates`, rather than picking one. `tree` takes `deep`.
- (2026-10-13) **Protocol 0.11 - properties: dotted paths, string lists, window text** - `gllAutomationServer.pas`. `get` / `set` reach through object properties (`Font.Size`, `Margins.Left`); a `TStrings` reads and writes as its text (`Lines`, `Lines.Text`; `Lines.Count` read-only), where `Lines` used to return the object's address as a number; an unpublished `Text` / `Caption` on a control falls back to its window text, so `TMemo.Text` is readable. A path ending on another object fails `NotScalar` with that object's properties; a `NoProp` list now includes object properties, flagged `nested`. New codes `Ambiguous`, `NotObject`, `NilObject`, `NotScalar`, `ReadOnlyProp`.

### Fixed
- (2026-10-13) **`keys` stalled after one stroke in a host without an application window** - `gllAutomationServer.pas`. The step markers were posted to `Application.Handle`; in a console test runner there is none, so they went nowhere and the sequence timed out with `strokesSent` 1. They now go to the server's own hidden window (`TKeyStepWindow`), which every host has once a `keys` request arrives. Found by the new test suite.
